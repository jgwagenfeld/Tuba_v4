Developer guide

Where the implementation lives

Tuba v4 is split around ownership boundaries: pipe model, solver export/execution/import, analysis artifacts, quick-look plotting, and reviewable browser scenes.

Module dependencies

Keep changes at the lowest ownership boundary that can solve the problem. Routing can propose geometry, but model mutation stays in the adapter. Solver output enters the review stack only through artifact parsing and result state creation. The arrows below read as feeds into.

  • tuba.builder → tuba.model
  • tuba.routing → tuba.routing.adapter → tuba.model
  • tuba.model → tuba.solver.aster
    • tuba.solver.aster → tuba.analysis
      • tuba.analysis → tuba.plotting
      • tuba.analysis → tuba.visualization → viewer/

Change ownership

Authoring produces intent, evidence records what the solver actually did, and review presents it. Work down this chain, never skip it.

Stage Owns
AuthoringBuilder methods, route requests, operations.
EvidenceSolver runtime, artifacts, parsers, provenance.
ReviewPlotting, web scene, reports, viewer metadata.

Visualization contract

Keep the two result-display paths distinct. tuba.plotting is the PyVista quick-look path for notebooks and exports. tuba.visualization plus viewer/ is the reviewable web-scene path. Choose one path per notebook or example.

Quick-look path

results.plot_deformed_stress(scale=40.0, model=model)

Reviewable scene path

scene = build_visualization_scene(model, result_states=[result_state])
bundle = write_scene_bundle(scene, "runs/demo_hot/review_scene")

How to extend autorouting

Keep routing changes in the routing package until a candidate is explicitly applied to the model. That keeps search, scoring, review, and model mutation separable.

Change Start here Verification
New request field tuba.routing.types Add route serialization and focused type tests.
New obstacle or space behavior tuba.routing.grid, tuba.routing.spaces Add grid occupancy tests and a route test through the new space.
New cost term tuba.routing.cost_model Assert the cost term, legacy summary, and selected-candidate order.
New loop family tuba.routing.expansion, tuba.routing.hybrid Add candidate geometry, reserved-envelope, and network-conflict tests.
New solver acceptance gate tuba.routing.solver_loop Use deterministic fixtures for unit tests and a real Code_Aster integration smoke when solver output is required.
New review output tuba.routing.report, tuba.visualization Update Markdown/JSON report tests and viewer scene-contract tests.

How to contribute

Start with CONTRIBUTING.md. It explains what counts as a Code_Aster-backed result, how export-only examples should be labeled, where solver execution lives, and which visualization paths are supported.

Contribution area Use this path
Modeling or export changes Keep model records in tuba.model, validation in tuba.validation, and Code_Aster file generation in tuba.solver.
Solver execution Use the native Tuba runtime bridge in tuba.solver.aster and tuba.solver.code_aster_runtime.
Result display Use tuba.plotting for PyVista quick-look views or tuba.visualization plus viewer/ for browser review bundles.
Examples and notebooks Label export-only examples as handoff/diagnostic workflows until Code_Aster has run and artifacts have been imported.
External interoperability Treat ada-py as reference material only unless a separate adapter and license decision is made.
