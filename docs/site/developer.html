Developer guide

Where the implementation lives

Tuba v4 is split around ownership boundaries: pipe model, solver export/execution/import, analysis artifacts, quick-look plotting, and reviewable browser scenes.

Module map

Module Owns
tuba.modelModel records, materials, sections, nodes, elements, supports, loads, operations, serialization.
tuba.builderCursor-based route authoring through model.pipe(...).
tuba.validationPre-export model invariants.
tuba.solver.asterCode_Aster study export, runtime execution, and result parsing.
tuba.solver.aster_meshstudy.mail mesh generation and analysis-mesh provenance.
tuba.solver.aster_commstudy.comm command-file generation.
tuba.analysisStudy, mesh, result-state, RMED, notebook, and artifact import helpers.
tuba.plottingPyVista quick-look and export helpers.
tuba.visualizationJSON scene contract and scene bundle writing for viewer/.
viewer/Three.js browser renderer for review bundles.

Visualization contract

Keep the two result-display paths distinct. tuba.plotting is the PyVista quick-look path for notebooks and exports. tuba.visualization plus viewer/ is the reviewable web-scene path. Choose one path per notebook or example.

Quick-look path

results.plot_deformed_stress(scale=40.0, model=model)

Reviewable scene path

scene = build_visualization_scene(model, result_states=[result_state])
bundle = write_scene_bundle(scene, "runs/demo_hot/review_scene")

Contribution rules

  • Do not present generated .comm, .mail, or .export files as completed solver results.
  • Do not fabricate stress, displacement, reaction, compliance, or clash-result values.
  • Keep Code_Aster execution native to Tuba. Shell, Docker, and legacy as_run paths are fallbacks.
  • Do not vendor or copy ada-py code. Treat ada-py as reference-only interoperability input.
  • When adding result display, route through tuba.plotting or tuba.visualization; do not add a third viewer path.
  • When adding examples, make export-only examples state that export is not completed engineering evaluation.
