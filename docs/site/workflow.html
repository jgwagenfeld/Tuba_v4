Workflow

Model, solve, review

This is the current v4 path. It is the same engineering sequence the legacy docs tried to teach, but it uses the actual v4 Python package, Code_Aster runtime bridge, artifact importer, and viewer contract.

Model, solve, review

Execution sequence

This is the order that matters during debugging. Each stage has a distinct output; if a later stage's output is missing, do not infer it from an earlier one. A written study.comm proves export only — it does not prove solver execution or parsed results.

  1. Build and validate — author the model, then model.validate(). Fix every reported error before export.
  2. Export the study — export_analysis_study writes .mail, .comm, .export, the manifest, and the sidecar. Handoff only.
  3. Run Code_Aster — on the configured runtime (WSL by default). Produces result tables and, when requested, an RMED file.
  4. Parse artifacts — the CSV/RMED tables are read into FEAResults (displacement, reaction, internal force, stress).
  5. Snapshot the state — wrap the results in a revision-tagged ResultState.
  6. Review — a PyVista quick-look or a web scene bundle.
solve_exported_study (used below) runs stages 3–4 in one call. model.solve() is the one-call convenience that runs stages 2–4 together; the staged path below is easier to debug because each stage's output is inspectable.

Two review paths

Imported result artifacts are the shared input: the parsed CSV tables, RMED, sidecar, and manifest that FEAResults is built from. From there, exactly two review paths are supported — choose one per notebook or example, and do not add a third.

  • PyVista — notebook quick-look, local export, engineering inspection.
  • Web scene — shareable bundle, object map, overlays, review state.

  1. Create a pipe-native model

    Define the material and section first, then build the route through the model.pipe(...) builder. Bends store explicit geometry so the solver, viewer, and compliance hooks do not infer it later. 

    from tuba import Model

model = Model(project_name="Demo")
model.add_material("Steel", E=210e9, nu=0.3, rho=7850.0, alpha=12e-6)
model.add_pipe_section("DN100", OD=0.1143, WT=0.00602)

with model.pipe(section="DN100", material="Steel", route="P-100") as b:
    b.start([0.0, 0.0, 0.0], support="anchor")
    b.run(2.0)
    b.bend_to([2.0, 1.0, 0.0], radius=0.8, plane_normal=[0.0, 0.0, 1.0])
    b.run(2.0)
    b.end(support="anchor")

  2. Define the operating state

    Operations are the higher-level scenario object. They convert to the load case data consumed by the Code_Aster writer. 

    hot = model.define_operation(
    "Hot",
    gravity=True,
    pressure=1.6e6,
    temperature=180.0,
    ref_temperature=20.0,
)

hot.add_field(
    "temperature",
    140.0,
    route_id="P-100",
    station_start=0.0,
    station_end=1.5,
)

model.validate()
    model.validate() collects semantic errors and raises them together: elements that reference a missing section or material, nodes that are not finite 3-vectors, zero-length elements, a pipe whose wall is too thick for its bore, invalid or colinear placement frames, unsupported operation-field quantities, and supports that point at a missing node. Fix the whole batch before exporting.

  3. Export and run Code_Aster

    The explicit solver object is easiest to debug. Export-only files are useful for inspection, but the evaluation is not complete until Code_Aster runs and result artifacts are imported. 

    from pathlib import Path
from tuba.solver.aster import CodeAsterSolver

solver = CodeAsterSolver(
    work_dir="runs/demo_hot",
    exec_method="wsl",
    wsl_distro="Ubuntu",
)

study = solver.export_analysis_study(model, "Hot", Path("runs/demo_hot"))
results = solver.solve_exported_study(model, study)
    Exported files: study.mail, study.comm, study.export, study_manifest.json, and study_tuba_fem.json. The sidecar maps shortened solver names back to Tuba objects.
    When a solve fails or is partial: the result CSV tables (study_depl.csv, study_effo.csv, ...) are missing or empty, and FEAResults accessors raise instead of returning zeros. Missing displacement or internal-force rows block result import outright; missing reaction, stress, or RMED files only limit downstream review. Read the runner log, do not present an empty or export-only study as a solved result.

  4. Load results safely in notebooks

    Use the shared notebook helper. With run_solver=False, the directory must already contain real Code_Aster result tables. 

    from tuba.analysis.code_aster_notebook import load_or_run_code_aster_results

run = load_or_run_code_aster_results(
    model,
    "Hot",
    "notebooks/code_aster_results/stress_analysis_operating",
    run_solver=True,
    exec_method="wsl",
    wsl_distro="Ubuntu",
)

results = run.results

  5. Review through one display path

    Use PyVista for local quick-look notebooks. Use the web-scene bundle for reviewable browser artifacts. Do not add a third result-display path.

    PyVista quick-look

    results.plot_deformed_stress(
    deform_scale=40.0,
    model=model,
    jupyter_backend="html",
)

    Web review bundle

    from tuba.analysis.code_aster_artifacts import import_code_aster_artifacts
from tuba.visualization import build_visualization_scene, write_scene_bundle

artifact = import_code_aster_artifacts(model=model, work_dir=study.work_dir, study=study)
scene = build_visualization_scene(
    model,
    analysis_meshes=[artifact.analysis_mesh] if artifact.analysis_mesh is not None else [],
    result_states=[artifact.result_state],
)
bundle = write_scene_bundle(scene, "runs/demo_hot/review_scene")

Completion boundary

The workflow is complete only when Code_Aster has executed and Tuba has imported the produced result artifacts. A generated study.comm, study.mail, or study.export file is a useful handoff artifact, not a solved stress, displacement, reaction, or compliance result.
