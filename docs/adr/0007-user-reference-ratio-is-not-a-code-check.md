# A user-supplied allowable may be shown as a screening ratio, never as a code check

The review may divide an element's finite-element von Mises stress by the allowable stress schedule the user authored on that element's material, and present the quotient as a **user reference ratio**. It is a screening scalar that makes a stress field readable by comparison; it is not an ASME B31 evaluation, not a utilization, not a compliance result, and the interface must never contain the words allowable, utilization, utilisation, code, or compliance in connection with it. The denominator's provenance travels with the number everywhere it appears, and where the ratio cannot be computed honestly it is unavailable, with the reason named.

We chose this over the two alternatives because both are worse and neither is a smaller change. Showing only the numerator leaves the product at the one thing every tool in this category is judged against: a stress plot without a denominator is a picture, and the reviewer's own question — "is this too much?" — has nowhere to go. Building a real B31 check is explicitly ruled out: [the B31J migration record](../architecture/b31j-compliance-migration.md) retires the built-in evaluator and states that no further standards implementation is planned, and ADR 0002 holds that generic FE von Mises stress never implies piping-code utilization. A user reference ratio is neither of those things. It performs no code equation, takes no code input, computes no stress intensity factor, applies no flexibility or stress-reduction factor, and knows nothing about load combinations, support stiffness limits, or thermal expansion ranges. It is one division, and the number on the other side of it is the user's own typed schedule.

The universal idiom in this category is exactly this scalar, and it is worth being precise about how thin it is. CAESAR II colours by percent of code stress to allowable and marks nodes at or above 100% in red; AutoPIPE's `Ratio` plot puts a `*` at ratio 1.0 and `FAIL` in its Notes column; CAEPIPE inverts to white-on-black above 1.00 and sorts stresses descending by ratio as its default idiom; PASS/START-PROF turns the failing cell red, the maximum-ratio cell yellow, and adds an error-code column with a hover message. None of them draws a code curve. The piping benchmark's first finding is that no tool in the category does — the verdict is a ratio, a colour band, and a text marker, and the same three things. What Tuba would be adding is not the scalar, which is the commodity, but an honest denominator for it, which is not: a competitor's ratio is a code result, and this one is visibly not.

Two failure modes in that benchmark set the constraints. Autodesk Inventor computes the same "safety factor" icon two different ways depending on whether the material dialog says yield or ultimate, so one screenshot carries two criteria and the reader is told neither. And CAESAR II reports an allowable of zero for a B31.1 operating case, which is arithmetically correct and which generated a forum's worth of "is this a bug?" reports — a number outside the domain of the calculation is indistinguishable, to the reader, from a number the tool invented. So the ratio's denominator is never hidden, and a temperature outside the schedule's span is **unavailable** rather than clamped, extrapolated, or zero.

The mechanics, since these are the parts that decide whether the number means anything. The numerator is the element's existing `max_von_mises`, unchanged, with its existing `compliance_role`. The denominator is `Material.allowable_stress`, already on the model, already temperature-indexed, and already populated with real descending schedules — `{20.0: 137e6, 150.0: 127e6}` and its variants appear in all seven of the authored examples that declare a material. It is evaluated at the load case's uniform `temperature_c` by linear interpolation between the bracketing schedule points; equal to a schedule point, that point is used. Elements reach their material through `metadata.material` on the scene object, which the builders already emit. The ratio is **unavailable** when the material declares no schedule, when the element has no material, when the case temperature falls outside the schedule's span, and — importantly — when the load case declares a temperature *field*. In that last case the uniform temperature is not the metal temperature at the hot spot, and evaluating the schedule there would understate the ratio exactly where it matters most. The scene currently carries only the uniform `temperature_c`; per-node temperatures exist in the solver path but do not reach the bundle, so the honest answer today is unavailable, and a per-element maximum sampled temperature is a follow-on data change rather than a change to this rule.

The scene must therefore carry the material table, which it does not today. `Material.allowable_stress` reaches the `materials` report table and the model script, and no part of the scene contract carries it, so this is a real schema addition and the reason this is a decision rather than a commit. It is additive: a model-level `materials` block alongside the existing objects, overlays and layers, leaving `visualization.scene.v1` intact because nothing in `VisualizationScene.validate()` treats the key set as closed. The ratio then appears in the existing "colour by" selector as an ordinary `ResultField`, which is what ADR 0006 requires — one colouring channel, one more field in it, no second ramp and no new surface.

The compliance caveat does the work that is left, and it is worth noticing that this is nearly free. ADR 0002 already routes every field through a `compliance_role` that `getComplianceNotice` renders wherever the field is tinting the scene, and the ratio takes a new value naming what it is — a screening ratio against a user-supplied schedule, not a code check. The existing machinery then places that notice beside the ratio in the viewport legend, the status strip and the field details without new code, and a screenshot carrying the ratio carries its own disclaimer. That is the whole argument for putting the disclaimer in the field rather than in a panel: it travels.

What this decision explicitly does not authorise. The sub-point field stays out of scope. Dividing Code_Aster's TUYAU section-point VMIS by an allowable schedule is much closer to what B31.3 does for self-allowed pipe, which is precisely why it must be a separate, later decision with its own scrutiny; deferring it is the cheap answer, not the safe one by default. The ratio does not gate anything — no issue is raised, no report section is omitted, no finding is created, and no other field is suppressed because a ratio is high. It does not replace or weaken the existing FE-stress caveat, which continues to state that the field is finite-element output. And no report table is added in this step; if a table is wanted, it is a separate change, and it inherits the same naming rule.

The open points a reviewer should settle before this is accepted. Whether the ratio is offered at all for models whose materials carry no schedule, or silently absent for them. Whether a user-authored screening factor — a 1.5 on 1.0, say, applied uniformly on top of the schedule — is in scope, or whether the schedule is the only denominator the product will ever use. And whether the element FE field is the right first surface, given that a piping engineer reads stress ratios on member end forces rather than on element von Mises, which would argue for reaching the ratio through `EFGE_ELNO` and a user-supplied stress class instead.
