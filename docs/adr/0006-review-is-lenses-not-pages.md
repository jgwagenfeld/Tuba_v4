# Review is lenses on one scene, not pages with presets

Navigation must never mutate the scene. The review stage offers one colouring channel — a single "colour by" selector over model properties and solver fields — one user-owned layer-visibility surface, and a persistent issues/annotations surface. Which lens you are looking through changes what is shown alongside the scene, never which layers are drawn or what tints them. Visibility is written only by the layer controls themselves; the colour map is written only by the colour control. The stage's entry state is the bundle's declared visibility.

We chose this over the former design, where the Model, Results and Issues tasks were peers and each carried a visibility preset (`TASK_VISIBILITY_PRESETS`) that rewrote the body and overlay layers on every switch. The tasks were not peers — one primary lens (results), one occasional lens (model identity), one cross-cutting overlay (issues) — and applying a preset on navigation fought the pinned display strip that already answers "what is drawn". The code carried the evidence: applying the preset at load switched off three of a composited view's four bodies on the screen built to show them, and a return from Build had to rebuild declared visibility by hand. Colour-by and visibility are separated because they answer different questions, so a change to one must not touch the other.

Prior art is unanimous. ParaView (and Salome-Meca's ParaVis, the engine this viewer already follows) puts visibility in the Pipeline Browser tree and colour in a separate Properties panel, with the Colour Map Editor and legend independently toggleable. Abaqus/CAE picks the field through one Field Output control and shows/hides through display groups. FreeCAD FEM has a single result pipeline dialog with a Mode and a Field selector beside tree visibility. SimScale colours from one Filters dropdown and toggles the legend separately. ANSYS Mechanical is the model for issues: suspect objects are highlighted in the Outline and listed in a persistent Messages window, never on a page you must navigate to. Even AsterStudy, Code_Aster's own GUI, keeps its Results tab a coarse workspace and still resolves colour by one field selector inside it. Coarse modality between pre- and post-processing is normal — that is this viewer's Build and Review stages, which stay — but a second, finer modality inside Review is not.

The consequences are additive: the Build/Review/Embed stages are unchanged, and the tab bar, `WORKFLOW_TABS` and per-task presets can be retired rather than replaced. Issues become an annotation and a companion list rather than a task, following ANSYS. The compliance caveat continues to ride with the colours, where it is least suppressible, rather than with whichever task happens to be open.
