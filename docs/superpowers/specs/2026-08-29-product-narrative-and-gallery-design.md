# Product narrative and viewer gallery

Date: 2026-08-29
Status: accepted

## Problem

A new user cannot tell what Tuba does.

The README is 377 lines. Its second section is a Documentation Map — a table of
where documentation lives, printed before the reader learns what the tool is.
Autorouting occupies 118 lines; the core workflow occupies 18. The title reads
`Tuba v4 ( work in progress)`.

`docs/content/index.md` is tight and accurate, and is currently the best
description of the product anywhere in the repository.

The viewer lands directly in a 3D scene. Its bundle picker lists ids run
through a titlecasing function (`Elements Supports Review`), with no
description of what any review shows or why it exists.

Every surface also speaks solver vocabulary. `examples.md` leads each entry
with `**Status: SOLVED / IMPORTED.**`, and the README's front matter is
Code_Aster runtime setup. Code_Aster is the solver, not the product.

## Objective

Tuba is a piping engineering platform. Code_Aster is an implementation detail
that should be invisible until the user wants to run their own analysis.

Hiding the solver is not concealing it. `AGENTS.md` requires that non-solver
values are never presented as solver results, and that a missing runtime fails
loudly. Evidence status stays visible on every published review; it stops being
the headline.

## Decisions

1. **Positioning**: piping engineering platform; the solver is plumbing.
2. **First contact is the browser.** A new user explores real solved reviews
   with no install. Code_Aster setup is the page they reach when they want
   their own model solved, not the front door.
3. **The viewer owns a gallery landing page.** Not the docs site — one click,
   one visual identity, and a shared bundle folder stays self-explaining
   offline.
4. **Thumbnails are generated by a script and committed.** No headless browser
   in the release path.

## Design

### 1. Registry metadata

`OfficialGallery` (`scripts/official_gallery.py`) gains three keyword-only
fields with no defaults, so a new gallery cannot ship unexplained:

```python
title: str    = field(kw_only=True)   # "Hot line expansion loop"
question: str = field(kw_only=True)   # "Where does a hot line move?"
summary: str  = field(kw_only=True)   # one or two sentences
```

`kw_only` places them after the defaulted fields without breaking the existing
positional entries.

Nothing else is added. The thumbnail derives as `gallery/<id>.png`. The
evidence badge derives from the existing `profile`:

| profile                                          | badge                      |
| ------------------------------------------------ | -------------------------- |
| `engineering-review`, `volume-engineering-review` | Results                    |
| `mesh-review`                                     | Mesh only — no results     |
| `model-review`                                    | Model only — no results    |

The badge carries the honesty requirement. It stays on every card; it is no
longer the heading. Attestation detail remains inside the review.

`write_bundle_catalog` emits objects rather than bare ids.
`validate_pages_tree` compares `[entry["id"] for entry in catalog]` against
`PAGES_BUNDLE_IDS`.

`question` is the load-bearing field: written as engineering questions, the
galleries read as a capability tour rather than a directory listing.

### 2. Viewer gallery landing page

`bundles.json` has three shapes in the wild and all must keep working:

- auto-discovered bare ids in development (`viewer/vite.config.js`),
- the literal `[]` emitted into the packaged shell,
- the published catalog from `write_bundle_catalog`.

The viewer normalises a bare string entry to `{id, title: <titlecased id>}`, so
development discovery and `viewer/scripts/make_bundle.py` recipes are
unaffected.

New module `viewer/src/gallery.js` renders cards from the normalised catalog.
Pure DOM: no Three.js import, no scene loading, no engineering calculation.

Cards are `<a href="?bundle=<id>">` anchors, not click-handled elements.
Keyboard navigation, middle-click and open-in-new-tab work without code, and
selecting a card is an ordinary navigation, so the existing boot path runs
unchanged on arrival. No second state machine.

The gallery renders only when all three hold: no `?bundle=`, not `?embed=1`,
and the catalog holds at least two entries. Otherwise behaviour is exactly as
today. The last condition preserves the existing contract that a standalone
bundle needs no catalog, so a shared single-bundle folder still opens straight
into its review, and existing `?embed=1` documentation embeds keep resolving a
default.

A header link back to `./` appears only when the catalog holds at least two
entries.

Consequences: `resolveBundleId`'s hardcoded default stops being reachable on
the bare `/viewer/` path, and the `pages-catalog` e2e scenario breaks by
design — it navigates to `/viewer/` and asserts the picker sits on
`code-aster-review`.

### 3. Thumbnails

`scripts/docs/generate_gallery_thumbnails.py`, beside the existing
`generate_figures.py`. It builds the development bundles, drives the existing
Playwright setup over `?bundle=<id>&embed=1` (embed mode already removes the
chrome), and writes `docs/content/assets/gallery/<id>.png`, committed.

The pages build copies them. Thumbnails join `_PAGES_REQUIRED_FILES`, so a
gallery cannot publish a card with a missing image. Staleness is the accepted
tradeoff, handled the way the hero image is handled today.

### 4. README

Target is roughly 70 lines: title without `( work in progress)`, one sentence,
hero image linking the live gallery, the three-step loop with a short authoring
snippet, a short install pointing at Setup, links out, licence.

Relocations, all to pages that already exist:

| README section                     | Destination      |
| ---------------------------------- | ---------------- |
| Code_Aster Runtime, Optional Features | `setup.md`    |
| Pipe Autorouting                   | `autorouting.md` |
| Quick Notebook Path                | `tutorial.md`    |
| Semantic Workflow Example          | `workflow.md`    |
| Section Catalog, Fragments, IFC    | `modeling.md`    |
| Documentation Map                  | deleted          |

Each block is diffed against its destination before the README loses it. Where
the destination already covers it, the README text is deleted; where it is
unique, it is moved. Nothing is dropped for looking redundant.

### 5. Documentation vocabulary

`examples.md` leads each entry with the engineering question, then what the
review shows, then the evidence badge as a trailing line. Same facts, reordered.
`index.md` keeps its shape and gains the gallery link.

### 6. Legacy cleanup

Verified against tracked files:

- Delete `tuba/visualization/scene_diff.py` (`build_scene_diff`,
  `apply_scene_diff`), its re-export, and its test. Exported public API with
  zero production callers. This is a public-API removal and belongs in release
  notes.
- Delete `labelForBundle` — superseded by registry `title`.
- Simplify `resolveBundleId` — its hardcoded fallback is no longer reachable on
  the bare path.
- Re-point the `pages-catalog` e2e scenario; add a gallery-cards scenario.

Explicitly **not** removed: root `imported_component_mixed_demo/` is read by
`notebooks/09_imported_component_mixed_system.ipynb`.

Untracked residue (`build/`, `.tmp-install-verify/`, `.vite/`,
`viewer/public/<bundle>/`, `notebooks/*.html`) is local only and already
covered by `git clean -fdX`.

## Testing

- Registry: every pages gallery has a non-empty `title`, `question`, `summary`,
  and a thumbnail file.
- Catalog: `bundles.json` ids equal `PAGES_BUNDLE_IDS`; the viewer normalises
  all three catalog shapes.
- Viewer: the gallery renders for a multi-entry catalog and does not render for
  a single-entry catalog, an `?embed=1` load, or an explicit `?bundle=`.
- Documentation: the existing registry-derived sync tests continue to hold; a
  README assertion keeps the hero and gallery links present.
- Full Python suite and the viewer's `node --test` suite pass.

## Out of scope

A browser-based model editor. Investigated separately and recorded here because
it motivates the gallery: with `gmsh`, `pyvista`, `h5py`, `meshio` and
`ifcopenshell` stubbed out, authoring, `validate()`,
`build_visualization_scene` and `write_scene_bundle` all succeed — the existing
viewer renders the result. Only `_compute_bend_nodes_gmsh`
(`tuba/solver/aster_mesh.py`) blocks mesh and study export, and bend node
positions feed the solver-input fingerprint, so a port must reproduce gmsh
placement exactly. That work gets its own specification.
