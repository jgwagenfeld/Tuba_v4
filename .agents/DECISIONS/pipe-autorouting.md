# Pipe Autorouting Decisions

## Decision 1 - Start With Deterministic Grid A*

Decision:

Use an internal 3D grid A* router as the first implementation.

Reasoning:

- Tuba needs a dependable first autorouter quickly.
- The existing model is centerline-based, so grid paths map naturally to `TubaModel` nodes/elements.
- A* is easy to test with small fixtures.
- Cost terms for length, bends, clearance, slope, and vertical movement are transparent to engineers.
- The route result is deterministic and easy to debug.

Rejected alternatives:

- **Deep reinforcement learning first**: too much training infrastructure, poor explainability, weak first-use reliability.
- **OMPL first**: strong planner, but state validity/collision integration would dominate the work before Tuba has basic routing semantics.
- **MILP/CP first**: attractive for exact constraints but heavier and less direct for a first working router.
- **Full CAD-kernel routing first**: unnecessary before centerline routing and engineering scoring are stable.

Revisit when:

- Single-pipe and multi-pipe deterministic routing are working.
- We have benchmark cases that show grid A* cannot produce acceptable routes.

## Decision 2 - Use Candidate Generation Before Solver Execution

Decision:

Generate multiple cheap route candidates first, then run expensive solver checks only on the top candidates.

Reasoning:

- Code_Aster runs are too expensive to put inside every grid expansion.
- Most bad candidates can be rejected by geometry, clash, support span, and approximate flexibility checks.
- This design allows Tuba to work even when Code_Aster is not installed.
- Candidate ranking creates reviewable alternatives for engineers.

Rejected alternative:

- Run Code_Aster for every route mutation. This is too slow and fragile for interactive routing.

## Decision 3 - Solver-In-The-Loop Is Optional and Nonfatal

Decision:

The solver loop must support export-only and no-solver modes.

Reasoning:

- The current development environment can export Code_Aster studies but may not have a working `as_run`.
- Piping engineers still benefit from geometry, clash, and support-span reports before solver execution.
- CI/local tests must not require Code_Aster.

Required behavior:

- `run_solver=False` exports studies and produces cheap scores.
- `run_solver=True` attempts real solver execution.
- Solver failure on one candidate does not erase all candidates.

## Decision 4 - Existing Pipes Become Obstacles for Later Pipes

Decision:

The first network router uses prioritized planning: route one pipe, reserve its clearance envelope, then route the next pipe.

Reasoning:

- This matches practical routing workflows.
- It is simpler than full multi-agent conflict resolution.
- It gives immediate value for multiple pipes.
- It can evolve into CBS-lite later.

Rejected alternative:

- Solve all pipes simultaneously in a global optimizer first. This is more complete but too large for the first implementation.

## Decision 5 - Fix Unique Element IDs Before Routing

Decision:

Element IDs must be generated by `TubaModel`, not by each `PipingBuilder`.

Reasoning:

- Autorouting creates many independent pipe runs.
- Current local builder counters can create duplicate `pipe_str_0` IDs.
- Solver result mapping and compliance reports depend on unique element IDs.

Required implementation:

- Add `TubaModel.next_element_id(prefix)`.
- Update `PipingBuilder`.
- Ensure JSON import keeps counters in sync.

## Decision 6 - Keep Routing Results Separate Until Accepted

Decision:

Routers return route candidates without mutating the model. A separate adapter applies the selected candidate.

Reasoning:

- Engineers need to compare alternatives before accepting a route.
- Solver-loop candidate evaluation may create temporary models.
- Avoiding mutation makes tests and retries simpler.

Required behavior:

- `GridRouter.route(...)` does not mutate `TubaModel`.
- `apply_candidate_to_model(...)` mutates intentionally and returns created element IDs.

## Decision 7 - Markdown and JSON Reports Are Required; HTML Is Optional

Decision:

Routing reports must always produce Markdown and JSON. HTML/3D export is optional.

Reasoning:

- The current PyVista HTML export can fail when optional trame dependencies are missing.
- A route review must still be available in headless environments.
- JSON output enables agent and regression workflows.

Required behavior:

- Missing visualization dependencies generate a diagnostic.
- Missing visualization dependencies do not fail routing.

## Decision 8 - Phase 1 Uses Orthogonal Routing

Decision:

Phase 1 routes along X/Y/Z directions only.

Reasoning:

- Most plant piping is orthogonal or rack/elevation driven.
- Orthogonal routing makes bend counts, spoolability, and support spans easier to reason about.
- It keeps A* state space and bend validation simple.

Rejected alternative:

- Allow arbitrary non-orthogonal routing first. Useful later, but it complicates bend catalogs and CAD-grade geometry.

Revisit when:

- We add bend catalogs or need aircraft/ship/offshore compact-space routes.

## Decision 9 - Start With Cuboid Obstacles, Then Mesh Accuracy

Decision:

Phase 1 obstacle occupancy must support cuboids reliably. Mesh/cylinder support can start approximate and improve later.

Reasoning:

- Existing tests already cover cuboid and STEP/mesh collision.
- Cuboids are enough to prove routing around equipment keepout volumes.
- Accurate mesh voxelization is a performance and implementation risk.

Required behavior:

- Cuboids are hard-blocking and inflated.
- Mesh obstacles can use conservative bounds in Phase 1.
- Postprocessed candidates still go through final collision checks.

## Decision 10 - Piping Engineer Trust Requires Explainability

Decision:

Every selected route must include a route report explaining why it was selected and what remains unchecked.

Reasoning:

- Piping engineers will not trust a black-box route.
- Candidate comparisons are more useful than a single output.
- Reports expose missing constraints and prevent overclaiming.

Required report sections:

- Inputs and assumptions.
- Selected route.
- Alternatives.
- Length, bends, elevations.
- Clash status.
- Support spans.
- Solver/compliance status.
- Known limitations.
